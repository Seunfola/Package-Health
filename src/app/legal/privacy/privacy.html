Privacy and Data Handling Policy

DepVault is built with a Zero-Trust, Zero-Code philosophy. We designed our architecture specifically so that enterprise users never have to worry about exposing intellectual property or proprietary source code.

0. Who Operates DepVault, and How to Reach Us

DepVault is currently operated by an individual, Folahan Mosunmola, not a registered company. For any question about this policy, or to request access to, correction of, or deletion of your data, contact Seunfola1@gmail.com. This policy is governed by the laws of Nigeria. Effective date: 4 August 2026.

1. Dependency and Repository Data

  • NO Source Code: DepVault NEVER uploads, scans, or touches your proprietary .ts, .js, or .py files.
  • Dependency Lists Only: The local CLI parses your package.json (or equivalent) locally and only transmits the names and versions of open-source dependencies (e.g., express@4.18.2) to our backend.
  • Private Packages: If you have internal private packages (e.g., @mycompany/auth), the backend will return a 404. We immediately discard this query and do not log or store private package names.

2. Historical Trending Data

To provide the "Time Machine" 30-day Trust Score graph, we store anonymized snapshots securely.

  • Data Stored: Ecosystem (e.g., npm), Package Name, Trust Score, Timestamp.
  • Data NOT Stored: Who requested the scan, IP addresses, or internal project names.

3. Account and Authentication Data

Signing in via GitHub, Google, or an enterprise SSO/OIDC provider shares basic profile information (your name, email, and provider account ID) with DepVault, which we store to identify your account and issue a session. We never receive or store your password for these providers. Where you connect the DepVault GitHub App to a private repository, we use only short-lived, scoped installation tokens generated by GitHub — DepVault never stores a long-lived personal access token on your behalf.

4. Organization Data

If you create or join an organization, we store the organization name, its members and their roles, pending invitations (by email), ownership-transfer requests, and an audit log of membership/role/ policy changes — this exists so organization admins can see who changed what. Configured notification-webhook URLs (Slack/Discord/xMatters/custom) are stored so alerts can be delivered; only organization admins can view or change them.

5. Profile Data

The optional User Profile page lets you add a display name, bio, links to your GitHub/LinkedIn/ Twitter, and upload a resume. If you upload a resume, DepVault reads it as text to try to prefill your email field — it does not perform full resume parsing (no name/experience extraction), and the raw uploaded file itself is not retained after this extraction step. Profile data (other than your email address) is visible to other signed-in users via the profile-by-username lookup; your email is never included in the "all profiles" listing used elsewhere in the product.

6. Notifications and Communications

DepVault stores in-app notifications about your repositories and, if you enable email notifications in your preferences, sends transactional email (e.g. security alerts) to the address from your connected sign-in provider. You can change these preferences, or disable email notifications entirely, from Settings at any time.

7. AI / Vector Search (Not Built Yet)

Semantic search over public vulnerability databases and package descriptions (to help detect malware/typosquatting heuristics) is a feature under consideration for the future, not something DepVault currently runs. No user data is processed by any AI/ML system today — this section will be updated with specifics if and when that changes.

8. CI/CD Gatekeeper Security

The GitHub Actions workflow (depvault-gatekeeper.yml) runs entirely within your own CI/CD runner. The execution, evaluation, and blocking of Pull Requests happens completely on your infrastructure.

9. Data Retention and Deletion

We keep account, organization, and scan-history data for as long as your account is active. Contact Seunfola1@gmail.com to request deletion of your account and associated personal data (profile, resume-derived fields, notifications); anonymized Trust Score history (Section 2) is not personal data and is retained for the product's historical trending feature.

10. CLI, MCP Server, and LSP Server Usage Telemetry

The DepVault CLI, MCP server, and LSP server send an anonymous usage ping by default whenever a scan tool is invoked — the tool name (e.g. scan_package_health), the ecosystem (e.g. npm), and a random identifier generated once per machine and cached locally. This identifier is never derived from your username, hostname, IP address, or any package or project name. We do not receive or store package names, file paths, or project identifiers from these pings — the same guarantee already made for Historical Trending Data in Section 2. This data is used only in aggregate, to understand how the tools are used and roughly how many distinct installs are active. Disable it entirely by setting DEPVAULT_TELEMETRY=0 in your environment.

11. Your Rights

Wherever you're located, you can ask us (at the contact above) to: tell you what personal data we hold about you, correct inaccurate data, delete your account and personal data, or export a copy of your profile/notification data. If you're in the EU/EEA, UK, or California, these map to your rights under GDPR/UK GDPR or the CCPA respectively — we'll honor equivalent requests regardless of where you're located, since as a small individually-operated project we'd rather apply one consistent standard than a patchwork of region-specific ones.
