LeakGuard — Secret Detection & Remediation

LeakGuard scans your working tree, staged changes, or a diff for hardcoded credentials — API keys, tokens, private keys, database connection strings — before they leave your machine. It runs on the same embedded engine as the Trust Score scanner: no separate binary to install, no subprocess, and nothing phones home unless you explicitly opt in.

$ depvault leakguard scan                 # scan the working tree
$ depvault leakguard scan --staged        # fast pass over what's about to be committed
$ depvault leakguard scan --fail-on high  # CI-style exit-code gate

Reading a result

Every finding reports a severity (CRITICAL/HIGH/MEDIUM/LOW), a liveness status, and a status. Liveness is not checked by default; --verify-live makes one real auth-probe request to the credential's own provider to confirm it still works — off by default, and the CLI asks for confirmation in an interactive terminal before sending anything. Status distinguishes an active finding from one matched by a depvault.json allowlist or that looks like a placeholder value (sk_test_..., AKIA...XXXX).

Nothing raw ever leaves the redaction boundary. A finding's match is always a redacted preview (first/last 4 characters) — the real value never appears in CLI output, CI logs, SARIF, or a dashboard sync.

Responding to a finding

$ depvault leakguard scan --playbook ./incident   # incident-playbook.md + per-finding rotation scripts
$ depvault leakguard scan --interactive             # walk through findings one at a time

Pre-commit and pre-push hooks

depvault hooks install --git installs two git hooks, scoped differently on purpose. Pre-commit runs a fast, staged-diff-only LeakGuard pass alongside the Trust Score gate on every commit. Pre-push runs a full working-tree LeakGuard scan once per push — the last local checkpoint before code actually leaves your machine, catching a secret that was already sitting in the tree (e.g. from before LeakGuard was installed, or committed with --no-verify) that a staged-diff-only check would never re-examine. Neither hook makes a network call — no liveness/blast-radius verification locally; that stays CI's job. Bypass either once with --no-verify (git commit --no-verify / git push --no-verify).

CI and the dashboard

The GitHub Action and both git hooks run the identical CLI under the hood, so a finding never disagrees between your terminal, CI, and your editor. In CI, results post as SARIF (visible in the repo's Security tab) and as part of the same PR comment as the Trust Score results — one combined report, not two competing bot comments.

Run depvault leakguard scan --upload (after depvault login) to sync a local scan to your dashboard — see a repository's detail page for the LeakGuard card once you have.

Configuration

{
  "leakGuard": {
    "failOn": "HIGH",
    "allowPaths": ["**/*.test.ts", "fixtures/**"],
    "allowValues": ["sk_test_FAKEFAKEFAKEFAKE"],
    "verifyLive": false,
    "blastRadius": false
  }
}

allowPaths excludes fixtures/examples from scanning; allowValues allowlists one exact known-fake value. verifyLive and blastRadius can only be turned on explicitly here or via their matching CLI flag — never implicitly.
