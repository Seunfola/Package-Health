Quick Start

Submit a GitHub repository URL, paste a package.json, or upload a manifest file directly from the homepage — no login required for public repositories. DepVault reads only the dependency manifest; your source code is never uploaded or stored.

Every scan produces a single Trust Score (0–100), weighted across four dimensions:

  • Security — 45%: known vulnerabilities, weighted by a Poisson CDF and the package's structural criticality.
  • License — 20%: penalizes non-permissive or toxic copyleft licenses (GPL, AGPL).
  • Maintenance — 20%: commit frequency, release cadence, and general repository health.
  • Popularity — 15%: weekly downloads and dependent count.

One scoring engine, the same mathematical pipeline, across four ecosystems:

Package managers are not ecosystems. npm, yarn, pnpm and bun all resolve from the one npm registry and share package.json, so they are a single ecosystem to the scoring engine. What differs is the lockfile and the remediation command — DepVault detects the manager (Corepack's packageManager field first, then lockfiles including bun.lockb) and prints a command you can actually run, rather than assuming one tool.

How scoring works

DepVault combines known vulnerability exposure, package criticality, maintainer diversity, freshness, maintenance, popularity, and license signals. Security contributes 45% of the Trust Score; license and maintenance 20% each; popularity 15%. Freshness adjusts maintenance, and Monte Carlo sampling can provide the displayed 95% confidence interval. The score helps compare choices; the finding list identifies urgent remediation work.

Analysis, accuracy & mathematics

DepVault is a multi-signal decision aid. It obtains registry metadata, download data, maintainer metadata, release timestamps, license information, and known-vulnerability data; normalizes those signals across ecosystems; then produces a score, a vulnerability list, and—when enabled—a deterministic uncertainty interval. It does not inspect your application code or prove a dependency is safe.

The score model

The base score is bounded to 0–100 and combines four normalized sub-scores:

Score = 0.45 × Security + 0.20 × License + 0.20 × (Maintenance × Freshness) + 0.15 × Popularity + Diversity adjustment
  • Security: CVSS base scores are summed into vulnerability burden B. A category prior w adjusts the Poisson rate: λ = B × (1 + w). The security score is 100 × P(X ≤ t | λ), where t is the configured risk tolerance. High attack-surface categories use w = 0.30, medium 0.15, and low 0.05.
  • Freshness: uses a true half-life: freshness = 2^(−days / halfLife). The default half-life is 365 days, so the factor is 0.5 at one year and 0.25 at two years.
  • Maintenance and popularity: are mapped to bounded scores from maintainer count and download volume. Maintenance is then multiplied by freshness, so stale packages cannot retain the full maintenance contribution.
  • License: evaluated as an SPDX expression, not a string match. Permissive scores 100, weak copyleft 60, strong copyleft and commercially restrictive terms 0, and a missing licence is treated as unknown rather than permissive. The "or later" suffix (GPL-3.0+, AGPL-3.0+) and compound expressions are handled properly: a disjunction such as MIT OR GPL-3.0 takes its safest operand because you may choose it, while a conjunction such as MIT AND GPL-3.0 takes its worst because you are bound by both.
  • Diversity: measures maintainer concentration with normalized Shannon entropy, H = −Σ pᵢ log₂(pᵢ). A normalized diversity value below 30 receives a 15-point penalty. Public email providers are treated as individual maintainers, not one shared organization.

Unavailable signals are excluded, never invented

When a signal cannot be obtained, its weight is redistributed across the signals that are known, and the gap is reported through data quality and confidence — it is never substituted with a constant. Two distinct cases exist:

  • Transient — a rate-limited or unreachable registry. Counted against the score's confidence.
  • Structural — the ecosystem has no such concept. Go module proxies expose no owners, download counts or licence, so those terms are excluded rather than scored as zero, and they do not count toward the "too many unknowns" cap that would otherwise pin every Go module below a passing grade.

This is why a report distinguishes scored low from could not be verified. A dependency nobody could check is a finding, not an absence — the summary counts it separately rather than dropping it.

Hard-stop conditions

The final score becomes 0 when vulnerability burden exceeds 20, or when a package is demonstrably abandoned — freshness below 0.15 where a real publish date exists, or zero maintainers where the ecosystem actually reports maintainers. The qualifiers matter: a missing date is not evidence of abandonment, and an ecosystem that has no maintainer concept must not be failed for it. These safeguards stop a high score in unrelated dimensions masking an extreme risk signal, without punishing a package for metadata its registry never publishes.

Confidence interval and accuracy

When Monte Carlo confidence is enabled, DepVault runs 1,000 reproducible simulations seeded from the lockfile hash. Each simulation perturbs severity by ±20% and downloads by ±10%, then recomputes the score. The displayed 95% interval is the 2.5th to 97.5th percentile of those results. It expresses sensitivity to this defined input-uncertainty model—not a statistical guarantee that a package is secure, and not a probability that an exploit will occur.

Accuracy principles: known vulnerability data is shown as findings rather than hidden inside a score; unknown or unreachable registry data is reported as unverified rather than turned into a fabricated low score; and the seeded simulation gives identical inputs identical confidence bounds in CI. Registry freshness, advisory coverage, metadata quality, and the qualitative category prior remain real limitations.

Where DepVault adds value

A conventional vulnerability audit answers whether its advisory database currently knows about a vulnerable version. DepVault retains that answer, then adds maintenance, freshness, license, popularity, diversity, category criticality, confidence bounds, and workflow enforcement across browser, CLI, editor, MCP, and CI. This makes it useful for prioritizing otherwise clean-looking packages and for applying a consistent policy before install or merge.

No unsupported superiority claim: DepVault is not documented as universally more accurate than every scanner. Its advantage is broader decision context and consistent enforcement surfaces. Use advisory IDs, package compatibility tests, and your security process alongside every Trust Score.

MCP Server — For AI Coding Agents

@deepvaultscan/mcp-server is published to the public npm registry and lets any Model Context Protocol-compatible agent (Claude Code, Cursor, Windsurf) check a package's Trust Score on demand. 

{
  "mcpServers": {
    "depvault": {
      "command": "npx",
      "args": ["-y", "@deepvaultscan/mcp-server"]
    }
  }
}
ToolUse it to
scan_package_healthScore a single package before adding it as a dependency.
scan_repositoryScore every dependency in a project's manifest at once.

Optional auto-scan on install: npx @deepvaultscan/mcp-server --enable-auto-scan persists an opt-in flag so future npm installs scan automatically; add --block-on-critical to fail an install that pulls in a known CRITICAL-severity vulnerability. Both are off by default and report-only unless explicitly enabled — every tool call requires live internet access, there is no offline mode for the MCP server.

Important: MCP auto-scan is a convenience feature, not an all-install interceptor. It runs when this package's own install lifecycle runs and cannot protect unrelated future npm install commands. Use CLI Shield hooks or GitHub Actions for an actual install or merge gate.

CLI — Shield & Install Hooks

The CLI is not yet published to the public npm registry — it's built from this project's source today. 

depvault shield express@4.18.2   # pre-scan one package, then install if it passes
depvault shield audit            # audit all currently installed packages
depvault hooks install           # print shell wrappers that gate npm/pnpm/yarn/pip/cargo/go installs
depvault scan --untrusted        # audit code you don't control — see below
Auditing code you don't control. depvault.json lives inside the repository being scanned, so a project can waive its own findings or mark its own dependencies trusted. That is the point of the feature for your own repo. When you are reviewing someone else's code, pass --untrusted: the policy is still parsed and every suppression it attempted is reported, but none are applied, and the threshold can only be raised — never lowered by the thing being audited.
# Build the CLI from this repository, then scan a project
pnpm install
pnpm --filter cli build
$ pnpm --filter cli exec depvault scan --path .

depvault shield <pkg> only gates the exact command you run. depvault hooks install is the real always-on gate — it prints shell functions that route every install through Shield first, blocking on a BLOCK verdict unless overridden with --force (audited, not silent).

Offline use: depvault shield sync downloads a signed verdict cache while online; if the backend later becomes unreachable, cached packages still get a real verdict — anything not already cached fails closed.

GitHub Actions

The composite action scores the checked-out manifest, writes a job summary, can update one pull-request comment, and fails the job when the average Trust Score is below your threshold. It runs on your GitHub runner and needs no account, backend, or API key.

# .github/workflows/depvault.yml
name: DepVault Scan
on: [pull_request]
jobs:
  scan:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      pull-requests: write # required only for PR comments
    steps:
      - uses: actions/checkout@v4
      - uses: Seunfola/package-health-backup/apps/github-action@v1
        id: depvault
        with:
          fail-below: '80'
          ignore-dev: 'false'
InputDefaultDescription
path.Directory relative to repository root.
fail-belowconfig valueMinimum average score; falls back to depvault.json.
risk-levelconfig / mediumlow, medium, or high.
comment-prtruePost or update one PR comment.
job-summarytrueWrite the Actions job summary.

The action exposes score, passed, and critical-count outputs. Pin to a release tag or commit SHA rather than a moving branch. Reporting runs before the final failure, so reviewers see package-level results even on a blocked pull request.

IDE extension & LSP intelligence

Every editor integration runs the same editor-agnostic @depvault/lsp-server over standard input/output. It analyzes package.json, requirements.txt, pyproject.toml, and Cargo.toml. Go manifests are supported by the CLI and GitHub Action, but are not currently an LSP manifest target.

What the language server does

  • CodeLens: where the client supports it, each dependency line shows [OK] DepVault Trust: 94/100, a warning, or a CRITICAL marker.
  • Hover: place the cursor on a dependency to see the full Trust Score report and suggested remediation.
  • Diagnostics: a score below the configured threshold becomes a warning; a CRITICAL known vulnerability becomes an error.
  • Quick fix: use the editor's code-actions menu to replace a vulnerable version with the recommended fixed version when one is available.
  • Update timing: the server re-analyzes after opening and saving a manifest, and debounces edits for 500 ms.
Network requirement: editor scoring needs package-registry data. If a registry is unreachable or rate-limited, DepVault reports that it could not verify the dependency; it does not fabricate a score of zero.

VS Code extension

Install the DepVault extension in VS Code, open a supported manifest, then adjust its settings under Settings → Extensions → DepVault or in settings.json. The extension requires VS Code 1.85 or later and bundles the language server with it.

{
  "depvault.scoreThreshold": 50,
  "depvault.enabledEcosystems": ["npm", "pypi", "cargo"]
}

scoreThreshold accepts 0–100 and defaults to 50. enabledEcosystems defaults to npm, PyPI, and Cargo. If you are building from this repository instead of installing a packaged extension, run:

$ pnpm --filter @depvault/lsp-server build
$ pnpm --filter depvault-vscode build
$ pnpm --filter depvault-vscode package
# In VS Code: Extensions → … → Install from VSIX

Neovim

Install the server globally, confirm that depvault-lsp-server is on your PATH, then add this configuration to init.lua for Neovim 0.11 or later:

vim.lsp.config('depvault', {
  cmd = { 'depvault-lsp-server', '--stdio' },
  filetypes = { 'json', 'toml', 'requirements' },
  root_markers = { 'package.json', 'requirements.txt', 'pyproject.toml', 'Cargo.toml', '.git' },
  init_options = {
    scoreThreshold = 50,
    enabledEcosystems = { 'npm', 'pypi', 'cargo' },
  },
})
vim.lsp.enable('depvault')
$ npm install -g @depvault/lsp-server
# In Neovim: K for hover; :lua vim.lsp.buf.code_action() for fixes

Neovim's built-in client does not render CodeLens text by default. Hover, diagnostics, and code actions work normally. Neovim 0.8–0.10 and nvim-lspconfig require a custom client registration; use the project’s Neovim integration README as the exact configuration source for those versions.

Sublime Text

Install the LSP package through Package Control, install the language server, then open Preferences → Package Settings → LSP → Settings. Add the following under clients:

{
  "clients": {
    "depvault": {
      "enabled": true,
      "command": ["depvault-lsp-server", "--stdio"],
      "selector": "source.json | source.toml | text.plain.requirements",
      "initializationOptions": {
        "scoreThreshold": 50,
        "enabledEcosystems": ["npm", "pypi", "cargo"]
      }
    }
  }
}

If your syntax package assigns a different scope to requirements.txt, change the selector accordingly. Sublime renders hover, diagnostics, and code actions; its LSP client does not render CodeLens.

JetBrains IDEs: IntelliJ, PyCharm, WebStorm, GoLand, and more

The JetBrains client is a Kotlin/Gradle plugin at apps/jetbrains-plugin. It uses the free LSP4IJ plugin to launch the same language server, rather than duplicating scoring and inspection logic. This integration is currently a scaffold: its source follows LSP4IJ's integration model, but it has not been build-verified against a live IntelliJ Platform SDK. Validate it in your target IDE before distributing it to a team.

  1. Install LSP4IJ from the JetBrains Marketplace: Settings → Plugins → Marketplace.
  2. Install the language server globally: npm install -g @depvault/lsp-server.
  3. From this repository, build the plugin: cd apps/jetbrains-plugin && ./gradlew buildPlugin.
  4. Install the generated build/distributions/depvault-jetbrains-*.zip via Settings → Plugins → Install Plugin from Disk….
  5. Open a supported dependency manifest and verify hover, Problems diagnostics, and quick-fixes.
JetBrains rollout checklist: first verify the pinned LSP4IJ and IntelliJ Platform versions with your installed IDE, confirm the server binary is discoverable on PATH, and test diagnostics and upgrade actions against a non-production project.

Data, privacy & limits

  • Live package scans use registry and OSV data. Shield's pre-synced verdict cache is the only offline fallback; uncached packages fail closed.
  • GitHub Action evaluation happens on your runner. PR comments need pull-requests: write, but a comment outage does not decide the gate result.
  • CLI, MCP, and LSP send anonymous aggregate usage telemetry. See the Privacy Policy for current data handling.
  • Scores, waivers, and explicit bypasses do not replace compatibility testing or your incident-response process.
